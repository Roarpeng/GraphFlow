01 / PRODUCT

重新定义 GraphFlow 的核心目标

不是单纯压缩源码，而是降低「一次正确完成任务」所需的模型工作量。

工程指标：成功任务平均费用 = 全部任务实际模型费用 ÷ 验收通过的任务数。不能只看输出 token 压缩率；必须同时核对正确率、返工轮数、延迟、误拦截率。
KEEP

坚持不做

模型路由与收费 API 代理、通用任务规划 Agent、云端对话记忆、模型训练平台、替代 Cursor/ZCode 的聊天 UI。

BUILD

继续深耕

精确上下文、可信代码编辑、最小充分验证、可授权的本地经验复用、任务级工具收益证据。

02 / AUDIT

先承认仓库已经有什么

现有能力代码事实仍需解决的缺口
gf_readAST 切片、类型闭包、Blast Radius、中英检索、搜索结果自适应截断、重复读取去重、AST/语义索引缓存、Git 分支范围隔离缺公开的输出预算参数、统一片段证据 ID、严格的按文件版本增量返回、跨调用准确率测试
gf_edit语法错误先拦截、批量内存预编辑、跨仓重命名、导出/签名/字段变更警告部分跨文件检查发生在写盘后；警告不等于拒绝；多文件写盘中断缺事务日志恢复
gf_exec基于反向导入的受影响测试选择（代码最大 6 跳）、输出压缩、原始日志归档、超时、3 次失败提醒缺可解释的选择依据、无关联测试的独立状态、失败指纹及强制继续条件、按风险升级验证
gf_macro重复读取/命令/编辑习惯挖掘、确定性脚本复用、Prompt Reflex、任务反射与 Git 同改文件习惯宏信任级别和审批不足；命令模板插值接 shell；独立生成 codemod 脚本绕开工具编辑门禁
风险优先级：先修复可导致错误写入/意外命令执行的路径，再提升检索效率。一次不安全修改引发的返工，可能抵消大量 token 压缩收益。
03 / FOUR TOOLS

四个工具逐项深化

gf_read / P1

渐进式证据读取

现状：已具备搜索截断及估算 token。新增：按预算分层输出「位置 → 摘要 → 代码 → 调用方/类型闭包」，支持上次证据版本的 Delta Read。

  • maxOutputTokens、detail=locate|summary|code|closure
  • sinceReceipt、cursor，保证可恢复而非静默截断
  • 返回精确 file:line-range、content_sha256、未读部分清单

验收：给定相同定位测试，命中率不能下降；重复调用若源码未变，只给简短引用；源码改变时不误用旧证据。

gf_edit / P0

带证据的变更事务

现状：先语法预检，后写盘并产生部分静态警告。新增：候选工作区内完成全部阻断检查，并提供预览与显式提交。

  • mode=prepare|commit、expectedSha256
  • 提交前检测：导出引用、签名、类型字段、导入解析、基线漂移
  • 跨文件使用事务快照及恢复日志；高风险变更需显式批准

验收：严重风险在写盘前拒绝；失败后文件哈希一致；提交冲突返回 STALE_BASELINE，不覆盖别人的改动。

gf_exec / P1

最小充分测试与失败诊断

现状：反向导入最大六跳和日志压缩。新增：记录选测原因、置信度及未覆盖范围，按实际改动风险选择测试层。

  • planOnly、verifyLevel=fast|safe|full
  • 结构化状态：PASS、FAIL、NO_TESTS、UNKNOWN、TIMEOUT
  • 错误指纹：文件、行、诊断码、stack root、关联 patch

验收：对照完整测试集测漏测率；错误摘要能定位到真正失败断言；无测试不可报 PASS。

gf_macro / P0

可信、可审计的零 LLM 复用

现状：两次相似操作可挖掘宏，Prompt Reflex 可直接触发。新增：宏信任状态机与动作权限。

  • discovered → proposed → approved → active → revoked
  • 参数化命令改用安全 argv/受控模板；无外部确认不执行有副作用的宏
  • 所有 codemod 一律走 gf_edit 的准备/提交事务

验收：未授权宏不执行；外部参数不能注入 shell；过期项目条件的宏只能重新审批。

04 / SHARED CAPABILITIES

真正值得新增的六项底层能力

01 / P0

Change Transaction

一次修改对应一份不可变的 prepare 提案、引用的源码哈希、风险清单和提交记录。统一所有写入入口，包括宏与 CLI。

02 / P0

Tool Benefit Ledger

只统计插件实际可观察的信息：返回字节、粗略 token 估算、命中率、重试/测试轮数、验证结果。实际 API usage 仅在宿主主动提供时记录，严禁伪称账单级精度。

03 / P1

Context Delta & Receipt

第一次读文件给可验证证据，第二次仅给变更片段；跨 Agent 交换证据 ID 而非重复搬运整段源码。遇到 hash 漂移则强制重新读。

04 / P1

Failure Fingerprint

将相同错误合并为一个指纹，识别「无新文件变更、无新错误信息、同一验证命令」的无效循环；自动提供最小诊断包，而非继续刷日志。

05 / P1

Verified Recipe Library

升级现有习惯挖掘：只有通过验证的操作才能晋升为可信配方；保存前置条件、文件适配范围、校验命令与失效边界。默认项目本地，不自动上传。

06 / P2

Semantic Confidence & Optional LSP

继续使用现有 AST/语义索引作为快速路径；对于跨语言/动态解析低置信度目标，可选调用已有 lsp-bridge.ts。无法确认时不把猜测当作精确引用。

重点：这是六个内部模块。从用户视角仍然只调用 gf_read、gf_edit、gf_exec、gf_macro，降低宿主工具菜单与提示词成本。

06 / CONTRACT

兼容性优先的接口设计

下列为拟新增字段，保持现有参数全部可用。先引入可选字段，再逐步启用阻断策略。

gf_read：严格预算与证据指针
{
  "targets": ["src/mcp-tools.ts#executeV3ToolCall"],
  "detail": "summary",              // locate | summary | code | closure
  "maxOutputTokens": 900,          // 硬上限；含提示与证据元信息
  "sinceReceipt": "read:sha256:...", // 可选，返回增量
  "cursor": null,
  "dedup": true
}
→ { "receiptId": "read:...", "contentHash": "sha256:...",
    "text": "...", "omitted": [...], "nextCursor": "...", "truncated": true }
gf_edit：写前准备 + hash 比对提交
{
  "mode": "prepare",
  "edits": [{"file":"src/a.ts","symbol":"processJob","newCode":"..."}],
  "policy": "strict", "verify": "affected"
}
→ { "proposalId": "edit:...", "baseHashes": {...},
    "risk": "medium", "blocking": [], "diff": "...", "proposedTests": [...] }

{"mode":"commit", "proposalId":"edit:...", "approved":true}
→ { "status":"COMMITTED|REJECTED|STALE_BASELINE|RECOVERABLE_FAILURE",
    "changedFiles":[...], "recoveryId":"..." }
gf_exec：验证计划与证据回执
{"cmd":"affected-tests", "verifyLevel":"safe", "planOnly":true}
→ {"selectedTests":[...], "selectionReasons":[...],
   "coverageStatus":"TARGETED|UNKNOWN", "planHash":"sha256:..."}

{"cmd":"affected-tests", "verifyLevel":"safe", "run":true}
→ {"status":"PASS|FAIL|NO_TESTS|UNKNOWN|TIMEOUT",
   "failureFingerprint":"...", "rawLogHandle":"...", "evidenceId":"..."}
gf_macro：无授权不执行有副作用的操作
{"action":"list", "includeProposals":true}
{"action":"approve", "id":"build_and_test", "scope":"workspace", "policy":"read-only"}
{"action":"run", "id":"build_and_test", "dryRun":true}
→ {"status":"WOULD_RUN", "steps":[...], "permissions":[...], "sourceHash":"..."}
上面的字段属于计划中的 API 草案，并非 v3.9.2 当前已支持参数。CLI/MCP 两层都需要同步修改及回归测试。
07 / DELIVERY

建议按 5 个批次开发，而非同时开工

0
Baseline · 可重复实验基线

冻结主分支基线、完成现有测试，建立 30–50 个真实仓库任务集：定位、改名、跨文件修改、测试修复、重复操作。记录有/无 GraphFlow 的耗时、token、成功率。

产出：benchmarks/task-suite.json / eval runner / baseline 报告。建议先在独立分支开展。
1
P0-A · 编辑事务与宏权限统一

先完成写前 guard，再加入完整的 prepare/commit、基线哈希与失败恢复。所有宏编辑路径都走事务。Prompt Reflex 只自动执行明确授权的低风险动作。

修改：surgical-edit.ts、macro-engine.ts、host-interceptor.ts、mcp-tools.ts；增加编辑事务与权限测试。
2
P0-B · 可观察的 Task Benefit Ledger

新增结构化工具回执与本地任务计数器。区分估算节省 token / 宿主提供的实测 usage / 成功任务三种信息，不混算。

修改：mcp-tools.ts、circuit-breaker.ts、flywheel.ts；新增 evidence-ledger.ts。
3
P1-A · 增量上下文 + 精准选测 + 失败指纹

输出预算与 receipt/增量读取；测试选择记录原因及置信度；相同失败提供救援包与下一动作建议。先在 dry-run 验证，再允许适配宿主 hook。

修改：slicer.ts、dehydrator.ts、circuit-breaker.ts、semantic-index.ts；新增 context-receipt.ts。
4
P1-B / P2 · 已验证配方 + 可选 LSP 精度升级

让宏只能从通过验证的记录升级，补齐撤销/失效。低置信度符号引用可选用 LSP 补证，无 LSP 时保留原有本地降级能力。

修改：task-reflector.ts、macro-engine.ts、lsp-bridge.ts、blast-radius.ts；建立多语言精度评测。
08 / ACCEPTANCE

验收不能只用「Token 少了多少」

指标测量方法建议门槛（目标，不是实测）
成功任务平均实付费用同一组任务、相同模型/价格/种子上下文，宿主提供真实 usage 时计算降低 ≥ 20%；没有 usage 时只报告估算输出量，不报告实付费用
任务验收成功率固定单测、人工审查和变更要求双门禁不得低于基线
修改前置安全故意导入破坏、签名漂移、并行冲突、磁盘中断测试所有已知高风险样例写前拦截；失败状态可恢复
检索质量每个真实任务标注目标符号与关键依赖Recall@k 不下降；P95 输出 token 降低 ≥ 20%
测试选择质量全量测试与候选测试集的失败发现对照已知相关失败不得漏报；不确定则升级或显式 UNKNOWN
宏安全Shell 注入、路径逃逸、未授权启动/删除、哈希漂移用例测试中未授权动作 0 次
性能热缓存读取 P50/P95、编辑准备时间、工程索引 RAM相比基线不得显著恶化；制定各语言/仓库规模单独阈值
建议做一个真实的对照实验：GraphFlow v3.9.2、GraphFlow 新版，均在同一宿主 Agent 下跑相同任务。除了平均值，还要看成本 P90/P95 与最差失败案例。
